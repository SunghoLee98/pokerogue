# 협동(Co-op) 모드 설계

- 작성일: 2026-10-12
- 상태: 초안 (사용자 승인 대기)
- 범위: 클래식 모드 위에서 동작하는 2인 협동 플레이

이 문서에서 "결정"은 사용자가 대화에서 정한 내용이고, "설계자 판단"은 사용자 확인 없이 설계자가 정한 내용이다. 설계자 판단은 리뷰 때 뒤집을 수 있다.

---

## 1. 의도와 목적

두 플레이어가 PokeRogue 클래식 런을 함께 진행한다. 각자 포켓몬 3마리를 맡고, 모든 전투는 플레이어 둘 대 적 둘의 2대2로 치른다. 협동 모드는 따로 떨어진 게임 모드가 아니라 클래식의 한 형태로 본다. 그래서 업적, 알, 도감, 캔디 같은 기존 로그라이크 진행 요소가 그대로 쌓여야 한다.

PokeRogue 본가는 계속 업데이트되므로, 협동 기능은 **코어 코드를 최소한으로 건드리고 바깥에서 감싸는 구조**여야 한다. 그래야 업스트림 변경을 머지할 때 충돌이 적다. 코어 수정이 불가피한 곳은 감수하되, 얇은 훅(hook) 한 줄 수준으로 줄인다.

## 2. 목표 / 비목표 / 실패 기준

### 목표
1. 웹 서비스 환경에서 두 사람이 인터넷을 통해 협동 플레이할 수 있다.
2. 같은 네트워크(LAN)나 같은 PC에서 로컬 소켓으로도 협동 플레이할 수 있다.
3. 1과 2는 **같은 통신 추상화** 위에서 동작한다. 게임 로직은 어떤 전송 방식을 쓰는지 모른다.
4. 스토리 전투(라이벌, 짐 리더, 사천왕, 악의 조직, 보스 등)를 포함한 모든 전투가 2대2다.
5. 각 플레이어는 최대 3마리를 소유한다.
6. 업적, 알, 도감, 캔디, 바우처, 언락이 각자 자기 계정에 정상적으로 쌓인다.
7. 전투에서 두 플레이어가 각자 독립적으로 행동한다. 둘 다 볼을 던질 수도 있고, 한 명은 볼을 던지고 다른 한 명은 공격하거나 아이템을 쓸 수도 있다.

### 비목표
- 3인 이상 플레이
- 엔드리스, 데일리, 챌린지 모드에서의 협동 (클래식만 대상)
- 방 목록, 로비, 매치메이킹, 친구 목록
- 대전(PvP)
- 서버 권위형 치트 방지 (협동이므로 신뢰 기반)

### 실패 기준 (돌아가더라도 실패로 보는 경우)
- 두 화면의 전투 결과가 서로 달라지는 경우(desync). 한쪽에서는 적이 쓰러졌는데 다른 쪽에서는 안 쓰러진 상황이 생기면 안 된다.
- 업스트림 PokeRogue를 머지할 때마다 협동 코드가 대규모로 깨지는 경우
- 협동 진행 때문에 솔로 세이브나 계정 데이터가 손상되는 경우
- 솔로 클래식보다 확연히 쉬운 경우 (보상이 두 배로 들어오는 등)

## 3. 사용자 흐름

### 3.1 연결 (결정)
1. 호스트가 타이틀에서 "협동 플레이 → 호스트"를 고른다.
2. 호스트는 **랜덤 참가 코드**를 받는다. 방 목록이나 로비는 없다.
3. 게스트는 "협동 플레이 → 참가"를 고르고 코드를 입력한다.
4. 연결되면 두 사람 모두 스타터 선택 화면으로 넘어간다.

### 3.2 스타터 선택 (결정)
- 각자 **자기 계정의 도감, 알, 캔디, 해금 상태**로 스타터를 고른다.
- 코스트 한도는 솔로 클래식 한도(`getRunValueLimit()`, 기본 10)의 **절반인 5**를 각자 가진다. (설계자 판단: 고정값 5가 아니라 `getRunValueLimit()`의 절반으로 계산해서, 이후 한도 변경에도 따라가게 한다.)
- 각자 최대 **3마리**를 고른다.
- 상대가 **확정한 포켓몬만** 내 화면 한쪽에 보인다. 커서 위치나 고민 중인 후보는 보이지 않는다.
- 둘 다 "시작"을 누르면 레디 상태가 되고, 두 명 모두 레디가 되면 게임이 시작된다.
- (설계자 판단) 레디 후 상대가 아직 고르는 중이면 레디를 취소하고 다시 고를 수 있다.

### 3.3 전투 (결정 + 설계자 판단)
- 필드 왼쪽(field index 0)은 호스트 포켓몬, 오른쪽(field index 1)은 게스트 포켓몬이다. (설계자 판단)
- 각자 **자기 필드 포켓몬에게만** 명령한다. 교체도 자기 3마리 안에서만 한다.
- 볼, 공격, 교체, 테라스탈을 서로 독립적으로 고른다. 둘 다 볼을 던지는 것도 가능하다. (요구사항 6)
- 도망가기는 둘 중 한 명만 골라도 시도한다. (설계자 판단, 기존 더블 동작과 같음)
- 야생 전투도 2대2다. 솔로에서 단일로 나오던 야생 웨이브도 협동에서는 적이 2마리 나온다. 야생 적 수는 `double` 값으로 정해지기 때문이다(4.4의 "단일 고정 전투" 참고).
- 원래 적이 1마리로 고정된 전투(클래식 최종보스, 적 1마리짜리 미스터리 인카운터)는 2대1로 치른다. 자세한 내용은 3.9.
- 같은 대상에게 둘 다 볼을 던지면 행동 순서상 먼저 던진 쪽이 판정되고, 잡혔으면 뒤의 볼은 던지지 않고 소모되지도 않는다. (설계자 판단)
- 잡은 포켓몬은 **던진 사람의 파티**로 들어간다. 이미 3마리면 기존 포켓몬과 바꾸거나 놓아준다.

### 3.4 쓰러짐과 게임 오버 (결정)
- 한 플레이어의 3마리가 모두 쓰러지면 그 플레이어의 필드 자리는 비고, 파트너 혼자 싸운다. 파트너의 후보 포켓몬이 빈자리로 들어가지 않는다.
- 쓰러진 플레이어는 "지원 모드"가 된다. 보상 차례는 그대로 돌아오고, 고른 아이템을 파트너 포켓몬에게 줄 수 있다.
- 누구든 부활 아이템(기력의조각 등)으로 쓰러진 포켓몬을 살리면, **다음 전투부터** 그 플레이어가 다시 참전한다.
- 게임 오버는 6마리가 모두 쓰러졌을 때뿐이다.

### 3.5 보상과 상점 (결정)
- 웨이브당 보상 선택은 **솔로와 똑같이 1회**다. 협동이라고 보상 총량이 늘지 않는다.
- 고르는 사람은 **웨이브마다 번갈아** 정해진다. 홀수 웨이브는 호스트, 짝수 웨이브는 게스트가 고른다.
- 고른 아이템은 **6마리 중 누구에게나** 줄 수 있다.
- 기다리는 사람은 상대 화면을 그대로 보고, "이거 골라줘" 같은 **핑**을 보낼 수 있다.
- 돈은 **공용 지갑**이다. 리롤과 구매는 그 웨이브에 고르는 사람이 한다. (설계자 판단)

### 3.6 진행 결정 (설계자 판단)
- 바이옴 갈림길과 미스터리 인카운터 선택지도 보상과 같은 순서로 번갈아 고른다. 상대는 핑만 보낼 수 있다.
- 진화, 기술 배우기, 특성 캡슐 같은 개별 포켓몬 관련 선택은 **그 포켓몬의 주인**이 한다.

### 3.7 계정과 진행도 (요구사항 4)
- 두 클라이언트는 각자 자기 계정으로 로그인한 상태다.
- 도감 "잡음" 기록, 캔디, 알 바우처, 업적, 언락은 **각자 자기 계정**에 쌓인다. 기존 `GameData` 경로를 그대로 쓴다.
- 상대가 잡은 포켓몬은 내 도감에 "봤음"으로 기록된다. (설계자 판단)
- 협동 클래식 클리어는 두 사람 모두에게 **클래식 클리어로 인정**한다. 클래식 클리어 시 받는 언락과 바우처도 똑같이 받는다. (설계자 판단)
- 바우처와 알 보상(클래식 클리어 바우처, 미스터리 인카운터의 알 등)은 **두 계정 모두** 받는다. 솔로로 같은 결과를 냈을 때 받는 것과 같다. 실패 기준의 "보상 두 배"는 런 안의 전력(아이템, 돈)에 관한 것이고 계정 보상은 해당하지 않는다. (설계자 판단)
- **런 도중 알 부화는 협동 중에 보류**한다. 부화 단계(`EggLapsePhase`, `EggHatchPhase`)는 계정마다 다르고 RNG를 소비해서 desync를 일으키기 때문이다. 걸음 수는 똑같이 쌓이고, 부화 연출은 런이 끝나 타이틀로 돌아갈 때 각자 진행한다. (설계자 판단)

### 3.8 세이브와 끊김 (설계자 판단)
- 협동 세션 세이브는 **양쪽에 같은 내용**으로 저장한다. 세이브에는 협동 메타데이터(참가자 ID, 소유권, 순서)가 포함된다.
- 솔로 세션 슬롯과 섞이지 않도록 **협동 전용 슬롯**을 둔다. 백엔드 수정이 필요하다(4.6 참고). (결정: 백엔드도 같이 고친다)
- 이어하기는 두 사람이 다시 같은 코드로 모였을 때만 가능하다. 두 세이브의 체크섬이 일치해야 한다.
- 연결이 끊기면 60초 동안 재접속을 기다린다. 그 안에 돌아오지 않으면 현재 웨이브 시작 지점으로 세이브하고 타이틀로 돌아간다.

### 3.9 단일 고정 전투 (결정 + 설계자 판단)

솔로 게임은 `checkIsDouble`(`src/battle-scene.ts`)에서 아래 전투를 무조건 단일로 만든다.

| 경우 | 모드 | 협동 대상 여부 |
|---|---|---|
| 최종보스 (`isWaveFinal`) | 클래식·챌린지 200웨이브, 데일리 50웨이브, 엔드리스 250의 배수 | 클래식 200웨이브만 해당 |
| 엔드리스 보스 (`isEndlessBoss`) | 엔드리스 50의 배수 | 해당 없음 (엔드리스는 비목표) |
| 미스터리 인카운터 | 전 모드 | 해당. 인카운터 설정이 정한 적 수를 따른다 |

클래식 10웨이브마다 나오는 야생 보스는 단일 고정이 아니다(확률로 더블이 됨). 협동에서는 일반 야생 웨이브와 같이 2마리가 나온다.

규칙:
- 협동에서 필드는 항상 더블(`double = true`)이다.
- 위 단일 고정 전투는 **적 수만 1로 고정**한다. 결과는 2대1이다.
- 미스터리 인카운터는 적을 인카운터 설정에서 따로 불러오므로 적 수가 이미 설정으로 정해진다. 적 1마리 설정이면 그대로 2대1이 된다.

**결정: 클래식 최종보스는 1마리 그대로 두고 2대1로 치른다.** 2마리로 늘리지 않는 이유:
- 솔로 최종보스도 이미 2단계에서 2대1이 된다. 1단계를 이기면 이터널이 무한다이맥스 폼으로 바뀌고 `currentBattle.double = true`가 되어 플레이어가 2마리를 내보낸다(`src/battle-scene.ts`의 최종보스 1단계 승리 처리). 협동 2대1은 이 원작 흐름과 같은 그림이다.
- 최종보스 로직은 보스가 1마리라고 가정한다. 1단계 최소 실드(`getMinimumSegmentIndex`), 폼 변경, 블랙홀 미니 아이템 부여, 대사가 모두 `isClassicFinalBoss` 기준으로 포켓몬마다 따로 돌아서, 2마리면 연출과 폼 변경이 두 번 일어난다. 이걸 막으려면 코어를 여러 곳 고쳐야 해서 최소 침투 원칙과 맞지 않는다.
- 이터널은 세계관상 유일한 존재라 2마리는 어색하다.
- (설계자 판단) 1단계가 솔로(1대1)보다 쉬워지는 점은 남는다. 실패 기준의 "솔로보다 확연히 쉬움"에 걸리면, 2마리로 늘리기보다 협동일 때 1단계 보스 실드 수를 늘리는 쪽으로 보정한다(`getEncounterBossSegments`에 훅 한 줄).

## 4. 기술 설계

### 4.1 전체 구조: 결정론적 락스텝 (설계자 판단)

두 클라이언트가 **같은 게임 전체를 각자 시뮬레이션**한다. 서로 주고받는 것은 **플레이어 입력**(행동 선택, 보상 선택 등)뿐이다.

이 방식을 고른 이유:
- PokeRogue 전투 로직은 이미 시드 기반으로 결정론적이다. `BattleScene.setSeed`, `resetSeed(waveIndex)`, `executeWithSeedOffset`, `randSeedInt`가 모두 `Phaser.Math.RND`를 쓴다. 시드를 공유하면 같은 입력에서 같은 결과가 나온다.
- 상태 동기화(서버 권위형) 방식은 포켓몬, 모디파이어, 아레나 태그 같은 전체 상태를 직렬화하고 적용하는 코드가 필요해서 코어 침투가 크다.
- 락스텝에서 전송되는 데이터는 작고 단순해서 전송 방식을 추상화하기 쉽다.

알려진 위험과 대응:
- **계정 데이터 의존성**: 시뮬레이션 일부가 로컬 계정의 `globalScene.gameData`를 읽는다. 두 계정은 데이터가 다르므로 그대로 두면 첫 웨이브부터 desync가 난다. 확인된 곳은 이로치 판정의 `gameData.trainerId`/`secretId`(`src/field/pokemon.ts`, 적 포함), 진화와 폼 변경 조건의 `dexData`(`pokemon-evolutions.ts`, `pokemon-forms.ts`), 알 기술 가용성의 `starterData`(`pokemon.ts`), `dexData`/`starterData`를 읽는 미스터리 인카운터(Weird Dream, Training Session 등)와 언락 검사다. 규칙은 다음과 같다. (설계자 판단)
  - **포켓몬 단위 값**(알 기술, 그 포켓몬의 진화 조건 등)은 **소유자의 데이터**를 쓴다. 필요한 값은 스타터 페이로드와 함께 보낸다.
  - **세계 단위 값**(적 이로치 판정용 trainerId/secretId, 인카운터 조건, 언락 검사)은 **호스트의 데이터 스냅샷**을 쓴다. 게임 시작 시 호스트가 `start` 메시지에 담아 보낸다.
  - 이 값을 읽는 지점에 `gameData` 대신 "시뮬레이션 데이터 소스"를 통하는 얇은 접근자를 둔다. 협동이 아니면 기존 `gameData`를 그대로 돌려준다. 이 작업은 4.4 표보다 많은 코어 파일을 건드린다(한 줄짜리 접근자 교체 위주). 원칙 5의 "감수" 범위로 본다.
  - 구현 1단계에서 `globalScene.gameData`를 읽는 전투/생성 경로를 전수 조사해 목록을 만든다.
- `randInt`(시드 없는 `Math.random`)이 게임 결과에 영향을 주는 곳이 있으면 desync가 난다. 현재 `src/data/status-effect.ts`, `src/battle.ts`, 일부 미스터리 인카운터(`global-trade-system`, `absolute-avarice`), `src/data/egg.ts`에서 쓰인다. 구현 첫 단계에서 이 사용처를 전수 조사하고, 게임 결과에 영향을 주는 것은 협동 중에만 시드 RNG를 쓰도록 바꾼다.
- 애니메이션이나 UI가 시드 RNG를 소비하면 화면 설정(전투 애니메이션 끄기 등)에 따라 RNG 순서가 달라질 수 있다. 조사 대상에 포함한다.
- **desync 감지**: 매 턴 끝과 매 웨이브 끝에 핵심 상태(양쪽 필드 HP, 상태이상, 파티 구성, 돈, RNG 상태)의 해시를 교환한다. 불일치하면 로그를 남기고 호스트 상태를 기준으로 재동기화하거나, 그게 불가능하면 세이브 후 중단한다. 1차 구현은 "감지와 중단"까지, 재동기화는 후속 과제다.

### 4.2 통신 추상화 (요구사항 1)

게임 로직은 아래 인터페이스만 안다.

```ts
interface CoopTransport {
  /** 호스트: 참가 코드를 발급받는다. */
  host(): Promise<{ joinCode: string }>;
  /** 게스트: 참가 코드로 접속한다. */
  join(joinCode: string): Promise<void>;
  send(message: CoopMessage): void;
  onMessage(handler: (message: CoopMessage) => void): Unsubscribe;
  onStatusChange(handler: (status: CoopConnectionStatus) => void): Unsubscribe;
  close(): void;
}
```

구현체:
- **`RelayWebSocketTransport`** (기본, 웹 서비스용): 중계 서버에 WebSocket으로 접속한다. 서버는 참가 코드를 발급하고, 같은 코드의 두 연결 사이에서 메시지를 그대로 전달하기만 한다. 게임 로직은 서버에 없다.
- **`LocalSocketTransport`** (로컬용): 브라우저는 TCP 소켓을 직접 열 수 없으므로, 호스트 PC에서 **같은 중계 서버를 로컬로 실행**한다(`pnpm coop:local`). 게스트는 호스트의 `IP:포트`로 접속한다. 이 경우 참가 코드는 `192.168.0.10:8787/ABCD` 같은 형태가 된다. 내부 구현은 WebSocket 전송을 재사용하고 URL만 다르다.
- **`LoopbackTransport`** (테스트용): 한 프로세스 안에서 두 클라이언트를 직접 연결한다. 자동 테스트에서 desync 검증에 쓴다.

중계 서버:
- 이 저장소 안에 `coop-server/`로 둔다. Node + `ws` 기반의 작은 독립 서버다.
- 기존 PokeRogue 백엔드(rogueserver)와는 별개의 서비스다. 통신 기능을 백엔드에 넣지 않는다. 로컬 모드에서 Go 서버와 MariaDB까지 띄우지 않아도 되게 하고, 백엔드 변경을 세이브 관련으로만 좁히기 위해서다. (설계자 판단)
- 웹 배포 시 중계 서버 주소는 `VITE_COOP_RELAY_URL` 환경 변수로 지정한다.
- 참가 코드는 6자리 영숫자, 10분 미사용 시 만료, 한 코드당 최대 2명이다.

메시지는 버전 필드를 가진 JSON이다. 클라이언트 게임 버전이 다르면 연결 단계에서 거절한다.

```ts
type CoopMessage =
  | { t: "hello"; gameVersion: string; protocol: number; accountName: string }
  | { t: "starters"; picks: CoopStarterPayload[]; ready: boolean }
  | { t: "start"; seed: string; hostWorldData: CoopWorldData } // 호스트만 보냄. 세계 단위 계정 데이터 스냅샷 포함
  | { t: "turnCommand"; turn: number; wave: number; command: TurnCommandPayload }
  | { t: "choice"; kind: CoopChoiceKind; wave: number; payload: unknown } // 보상, 바이옴, ME, 진화 등
  | { t: "ping"; kind: CoopChoiceKind; payload: unknown }
  | { t: "checksum"; wave: number; turn: number; hash: string }
  | { t: "bye" };
```

### 4.3 협동 세션 계층

코어 바깥에 `src/coop/` 디렉터리를 새로 만든다.

- `CoopSession`: 현재 협동 세션의 단일 진입점. 로컬 플레이어 역할(호스트/게스트), 소유권 표, 보상 순번, 전송 객체를 가진다. 협동이 아닐 때는 `null`이고, 모든 협동 분기는 `coopSession?.` 한 번으로 끝난다.
- `CoopOwnership`: 각 `PlayerPokemon.id` → 소유자(호스트/게스트) 매핑. 세션 세이브에 포함된다.
- `CoopInputBroker`: "이 입력은 누가 내야 하는가"를 판단한다. 로컬 플레이어 차례면 기존 UI를 띄우고 결과를 전송한다. 상대 차례면 대기 화면을 띄우고 원격 입력이 오면 그 입력을 기존 핸들러에 그대로 넣는다.
- `CoopStarterBridge`: 상대 스타터 페이로드를 받아 내 시뮬레이션에서 `PlayerPokemon`을 만든다.

### 4.4 코어 연결 지점 (최소 침투)

코어 파일 수정은 아래 지점의 **훅 호출 추가**로 제한한다. 각 훅은 협동이 아닐 때 아무 일도 하지 않는다.

| 지점 | 파일 | 바뀌는 동작 |
|---|---|---|
| 게임 모드 | `src/game-mode.ts` | 클래식 설정에 `isCoop` 플래그 추가. `GameModes`에 새 모드를 만들지 않고 클래식을 재사용한다 (설계자 판단, 클래식 클리어 인정과 업적 경로를 그대로 쓰기 위함). |
| 더블배틀 강제 | `src/battle-scene.ts` `checkIsDouble` | 협동이면 항상 `true`. 마지막 웨이브와 미스터리 인카운터 예외도 협동에서는 무시한다. |
| 단일 고정 전투의 적 수 | `src/battle.ts` 생성자(`enemyLevels`) | 야생 전투는 적 수를 `double ? 2 : 1`로 정하므로, `double`만 강제하면 최종보스가 2마리 나온다. 협동에서 원래 단일 고정이었던 웨이브(클래식 최종보스)는 `double`과 별개로 적 레벨 배열을 1개로 만든다. 3.9 참고. |
| 미스터리 인카운터 더블 | `src/data/mystery-encounters/utils/encounter-phase-utils.ts` `initBattleWithEnemyConfig` | 인카운터 전투는 `battle.double`을 설정값으로 다시 덮어쓴다. 협동이면 `true`로 둔다. 적 수는 인카운터 설정 그대로다. |
| 스토리 전투 | `src/battle-scene.ts`, `fixed-battle-configs.ts` | 고정 전투도 `double` 강제. 트레이너 1명이 2마리를 동시에 내보낸다. |
| 볼 사용 제한 | `src/phases/command-phase.ts` | 볼/도망 선택 시 반대편 명령을 `skip`하는 두 곳(`handleFieldIndexLogic`, 볼 처리부)에서 협동이면 볼은 건너뛰지 않는다. 도망은 기존대로. |
| 명령 입력 | `src/phases/command-phase.ts` `start` | 해당 field index의 소유자가 로컬이 아니면 UI 대신 `CoopInputBroker`에서 원격 명령을 기다린다. |
| 포획 | `src/phases/attempt-capture-phase.ts` | 대상이 이미 잡혔으면 볼을 소모하지 않고 종료. 잡은 포켓몬 소유권을 던진 사람으로 등록. 파티 가득 참 판정을 "던진 사람 소유 3마리"로 바꾼다. |
| 파티 크기 | 스타터 화면, 포획, 보상 | `PLAYER_PARTY_MAX_SIZE`(6)는 그대로 두고, 협동에서는 소유자별 3마리 한도를 추가로 검사한다. |
| 교체 | 파티 UI, `SwitchPhase`, `SummonMissingPhase` | 자기 소유 포켓몬만 선택 가능. 한쪽 전멸 시 빈자리를 상대 후보로 채우지 않는다. |
| 보상 선택 | `src/phases/select-modifier-phase.ts` | 순번 플레이어만 입력하고 상대는 대기와 핑. 대상 포켓몬은 6마리 전체에서 고른다. |
| 바이옴/ME 선택 | `select-biome-phase.ts`, `mystery-encounter-phases.ts` | 보상과 같은 순번 규칙 |
| 개별 선택 | `learn-move-phase.ts`, `evolution-phase.ts` 등 | 포켓몬 주인이 입력 |
| 세이브 | `src/system/game-data.ts`, `src/@types` 세션 타입 | 세션 데이터에 `coop` 블록 추가, 협동 전용 슬롯 번호 사용 (백엔드 4.6과 짝) |
| 도감과 진행도 | `src/system/game-data.ts` | "잡음" 기록은 소유자 계정에만, 상대 클라이언트는 "봤음"만 기록 |

필드 위치 규칙: 필드 0번은 호스트 소유 중 살아 있는 첫 포켓몬, 필드 1번은 게스트 소유 중 살아 있는 첫 포켓몬이 되도록 파티 순서를 유지한다. 파티 배열 자체는 6칸 하나를 그대로 쓴다(코어 구조 유지).

### 4.5 스타터 페이로드

상대 스타터를 내 쪽에서 똑같이 만들려면, 상대 계정에서만 알 수 있는 정보를 모두 보내야 한다.
- 종, 폼, 성별, 이로치와 변종, 특성 인덱스, 패시브 해금 여부, 성격, 개체값, 기술 구성(알 기술 포함), 테라 타입, 우정, 포켓볼, 닉네임
- 생성 후에는 협동 중 `PlayerPokemon` 생성이 로컬 `gameData.starterData`를 읽지 않도록 한다. 소유자 페이로드가 기준이다.

### 4.6 백엔드(rogueserver) 변경 (결정: 백엔드도 같이 고친다)

백엔드는 별도 저장소 `pagefaultgames/rogueserver`(Go, AGPL-3.0)이고, 사용자 포크 `SunghoLee98/rogueserver`에서 수정한다. 백엔드는 계정, 세이브 저장, 클리어 기록, 데일리 시드만 담당하고 게임 로직은 없다. 변경은 세이브 관련으로 좁힌다.

확인된 현재 동작:
- 런 세이브는 `defs.SessionSaveData` 구조체로 디코드한 뒤 gob으로 저장한다. **구조체에 없는 필드는 저장 시 사라진다.** 그래서 프론트엔드에 `coop` 블록을 추가하는 것만으로는 보존되지 않는다.
- 세션 슬롯 수는 `defs.SessionSlotCount = 5`로 고정이고, get/update/delete/clear/newclear가 모두 이 범위를 검사한다.
- `newclear`는 "이 계정이 이 시드를 처음 클리어했는가"를 계정별로 판정한다. 두 계정이 같은 시드로 클리어해도 각자 기록되므로 **협동 클리어 인정에는 변경이 필요 없다.**

변경 내용:
1. `defs.SessionSaveData`에 ``Coop *CoopSessionData `json:"coop,omitempty"` `` 필드를 추가한다. 내용은 프론트엔드 `coop` 블록과 같다(참가자 계정 이름, 역할, 소유권 표, 보상 순번, 프로토콜 버전). 솔로 세이브에는 나타나지 않는다.
2. 협동 전용 슬롯 1개를 추가한다. 기존 0~4는 솔로 그대로 두고, 슬롯 번호 5를 협동 전용으로 쓴다. 슬롯 범위 검사를 "솔로 0~4 또는 협동 5"로 바꾼다. (설계자 판단: 슬롯 1개. 협동 런은 한 번에 하나만 진행한다.)
3. 협동 슬롯은 `coop` 필드가 있는 세이브만 받고, 솔로 슬롯은 `coop` 필드가 있는 세이브를 거절한다.
4. 기존 저장 데이터와 호환된다. 필드가 추가될 뿐 스키마 마이그레이션은 없다.

호환성 원칙: 수정된 프론트엔드가 **수정되지 않은 백엔드**에 붙으면 협동 메뉴를 숨긴다. 연결 시 슬롯 5 조회가 범위 오류를 내는지로 판단한다. 솔로 플레이는 어느 조합에서도 영향이 없어야 한다.

### 4.7 핑
- 상대 차례일 때 화면의 선택지에 커서를 두고 핑 버튼을 누르면, 상대 화면의 그 선택지에 표시가 뜬다.
- 결과에는 영향을 주지 않으므로 desync와 무관하다.

## 5. 테스트 전략
- `LoopbackTransport`로 두 개의 게임 인스턴스를 한 테스트 안에서 돌리고, 웨이브마다 체크섬이 같은지 검증한다.
- 기존 `test/` 구조(vitest, `GameManager`)를 따른다.
- 필수 시나리오: 둘 다 볼 던지기, 한 명 볼 + 한 명 공격, 같은 대상 이중 포획, 한쪽 전멸 후 부활, 보상 순번, 라이벌/보스 2대2, 클래식 최종보스 2대1(적 1마리 유지, 2단계 폼 변경 정상), 적 1마리 미스터리 인카운터 2대1, 협동 세이브 후 이어하기, 버전 불일치 거절.
- 중계 서버는 별도 단위 테스트(코드 발급, 2인 제한, 만료, 메시지 전달).
- 백엔드는 rogueserver의 기존 Go 테스트 방식을 따른다: 협동 필드 왕복 보존, 슬롯 5 범위 허용, 솔로/협동 슬롯 교차 거절.

## 6. 구현 순서 제안
1. 결정론 보장 (desync의 근본): `randInt` 사용처 조사, `gameData` 의존 지점 조사와 시뮬레이션 데이터 소스 도입
2. `CoopTransport` 추상화, `LoopbackTransport`, 중계 서버
3. `CoopSession`과 소유권, 게임 모드 플래그
4. 연결 UI(호스트/참가)와 스타터 선택(5코스트, 3마리, 상대 확정 픽 표시, 레디)
5. 전투: 2대2 강제, 명령 분배, 볼 독립 사용, 포획 소유권

8. 백엔드(rogueserver 포크) 협동 필드와 슬롯, 이어서 프론트엔드 세이브, 이어하기, 재접속, 체크섬 desync 감지
9. 계정 진행도(도감, 업적, 알) 검증
